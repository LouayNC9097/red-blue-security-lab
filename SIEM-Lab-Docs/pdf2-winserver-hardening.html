What this guide is. It does three things, in order: it audits your Windows Server from Kali, it hardens it, and it then deliberately generates suspicious activity on your own server so you can prove Wazuh detects it. That last part is the whole point — a detection you have never seen fire is not a detection, it is a hope.

Scope — read this before you start

Being precise about this is not bureaucracy. It is the professional habit, and it is why penetration testers get to do interesting work legally.

Everything in this guide targets one machine you own

Every command here runs against 10.0.0.50 — a VirtualBox VM on your own laptop, on an isolated network segment with no route to anything. There is no third-party system here, no wordlist, and no credential attack of any kind. Where authentication events are needed for a detection test, you use a throwaway account you created yourself and a single password you deliberately mistype, so that log events exist to be detected. You are generating log volume to test a sensor, not attempting to access anything.

P0  Windows for a Linux person

You will be much faster if this section is read rather than skipped. Every concept here trips up Linux people, and all of them matter for the work ahead.

P0.2 Two facts about Windows security you cannot skip

1. Windows denies by default, Linux allows by default

An empty firewall ruleset on Windows blocks everything inbound. This will bite you the very first time: the Wazuh agent ships, starts, and then sends nothing, because Windows Firewall silently drops inbound port 1514. You will lose an afternoon to this if nobody tells you. Part P2.4 has the fix.

2. Event ID 4624 is logged by default; the useful ones are not

A default Windows Server logs successful and failed logons and little else. No process creation. No detailed file access. No privilege changes. Part P4.4 turns on the auditing your SIEM needs — and that section is the single highest-value part of this entire guide, because without it Wazuh will be nearly blind on Windows.

P1  Prepare WinServer in the lab

P1.1 Current state, and the problems it causes

WinServer currently has a single adapter on intnet and no internet connection. That is fine for isolation, and it is a problem for installing an agent. Also worth noting from the VM config: the install ISO is still attached to the DVD drive.

P1.2 Snapshot first. Always.

Do this before any other step

Power off WinServer in VirtualBox and take a snapshot named winserver-clean-30sep. Everything from here on is reversible in about a minute, which turns every remaining risk into a non-event.

P1.3 Give it internet, or commit to air-gap — your choice

Option A — add a NAT adapter (recommended)

Same pattern you used for Kali yesterday: keep intnet for lab traffic, add NAT purely for internet. Requires the VM powered off.

VBoxManage modifyvm "WinServer" --nic1 none
VBoxManage modifyvm "WinServer" --nic2 intnet --cable2 on
VBoxManage modifyvm "WinServer" --nic3 nat   --cable3 on
VBoxManage modifyvm "WinServer" --natpf3 "winrm,tcp,127.0.0.1,15985,,5985"
VBoxManage startvm "WinServer" --type headless
Get the adapter slot number right — you have been here before

--natpf1, --natpf2, --natpf3 refer to the adapter slot number, not to “the NAT one”. Above I moved intnet to slot 2 and NAT to slot 3, so the forward uses --natpf3. Using the wrong number writes the rule into a disabled block, reports no error at all, and does nothing. Always verify:

VBoxManage showvminfo "WinServer" | Select-String "NIC|Rule"

Simpler alternative: keep intnet in slot 1, add NAT in slot 2, and use --nic2 nat --natpf2 exactly as you did for Kali. Either is fine — just match the number to the slot.

Option B — stay air-gapped and sideload the agent

More realistic for a hardened server, and it forces you to learn offline installation — a genuinely useful skill. No adapter changes at all.

On the Windows host, download the agent installer once:

# PowerShell on your Windows 11 host
curl.exe -o "$env:USERPROFILE\Downloads\wazuh-agent-4.14.8-1.msi" `
  https://packages.wazuh.com/4.x/windows/wazuh-agent-4.14.8-1.msi

Share that folder with the VM through VirtualBox — run this on the host shell:

VBoxManage sharedfolder add "WinServer" "wazuhmsi" `
  --hostpath "C:\Users\pc\Downloads"

Then inside the VM, from an Administrator PowerShell. Guest Additions maps the share to \\tsclient\wazuhmsi:

msiexec.exe /i "\\tsclient\wazuhmsi\wazuh-agent-4.14.8-1.msi" /q `
  WAZUH_MANAGER="10.0.0.40" WAZUH_AGENT_NAME="winsrv-01" `
  WAZUH_AGENT_GROUP="windows,servers"

Verify the share is visible from inside the VM before trying the install:

Get-ChildItem "\\tsclient\wazuhmsi" | Select-Object -First 5 Name, Length

P1.4 Detach the ISO and set a static address

Detach the install media

VBoxManage modifyvm "WinServer" --medium none
VBoxManage showvminfo "WinServer" | Select-String "DVD|ISO"

Should now show no DVD image attached. This prevents a boot-into-setup surprise later.

Set the lab IP

Open an Administrator PowerShell on the server. First find out what your adapter is actually called — do not guess:

Get-NetAdapter | Format-Table Name, InterfaceDescription, MacAddress, Status -AutoSize
Get-NetIPAddress -AddressFamily IPv4 | Format-Table InterfaceAlias, IPAddress, PrefixLength
The lesson from Ubuntu, applied to Windows

On Ubuntu the netplan file silently discarded your static IP because of one misspelled key. Windows has the same class of problem: an address applied incorrectly survives until the next reboot and then vanishes. The permanent methods are the NetTCPIP cmdlets or netsh interface ip set address. Verify with a reboot, exactly as you did before.

# 10.0.0.50 on the intnet adapter. Replace "Ethernet" with YOUR adapter name from above.
Set-NetIPInterface -InterfaceAlias "Ethernet" -Dhcp Disabled
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 10.0.0.50 -PrefixLength 24

# Equivalent, if you prefer netsh:
netsh interface ipv4 set address name="Ethernet" static 10.0.0.50 255.255.255.0

Verify — and verify again after a reboot:

Get-NetIPAddress -InterfaceAlias "Ethernet" -AddressFamily IPv4
ipconfig

Rename-Computer -NewName "WINSRV-01"; Restart-Computer

Never work with a server called WIN-4F2K9D8Q7P3A. Hostnames appear in every log line, every alert and every report.

P2  Enroll it in Wazuh

Once this works, everything from Part P5 onwards becomes possible: you can see what the server is doing instead of guessing at it.

P2.1 The enrolment flow, in order

1. Register→ 2. Install agent→ 3. Open firewall 1514→ 4. Verify Active→ 5. Confirm alerts flow
Step 3 is where this almost always fails. Do not skip it.

Windows Firewall blocks inbound TCP by default. The Wazuh agent installs cleanly, starts, shows as running — and silently sends nothing. This is the most common Windows enrolment failure there is, and it looks exactly like a Wazuh problem.

P2.2 Register the agent

In the dashboard: Agents → Add agent → Windows. Fill in:

  • Name: winsrv-01 — matches the hostname you set in P1.4
  • IP: 10.0.0.50/24
  • Tags: os.windows,role.server,env.lab

Copy the generated PowerShell command. Note the key is unique to this agent.

P2.3 Install the agent

On WinServer, in an Administrator PowerShell. Either use the command the dashboard generated, or do it in explicit steps so you can see what is happening:

# 1. download (Option A with NAT). Skip this line if you sideloaded.
Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.14.8-1.msi `
  -OutFile $env:TEMP\wazuh-agent.msi

# 2. install silently, pointing at the lab IP
$msi = "$env:TEMP\wazuh-agent.msi"
Start-Process msiexec.exe -ArgumentList @(
  "/i", $msi, "/quiet",
  "WAZUH_MANAGER=10.0.0.40",
  "WAZUH_AGENT_NAME=winsrv-01",
  "WAZUH_AGENT_GROUP=windows,servers"
) -Wait

# 3. start it and make it survive reboot
Set-Service -Name "Wazuh" -StartupType Automatic
Start-Service -Name "Wazuh"
Get-Service -Name "Wazuh"     # expect: Running

Where the agent keeps its configuration, mirroring Linux:

Get-Content "C:\Program Files (x86)\ossec-agent\ossec.conf" |
  Select-String "server|port|agent_name|labels"
Get-Content "C:\Program Files (x86)\ossec-agent\wazuh-agent.conf" | Select-Object -First 40

P2.4 Open the firewall — the step everyone misses

# Inbound rule for the agent listener
New-NetFirewallRule -DisplayName "Wazuh Agent 1514" `
  -Direction Inbound -Action Allow -Protocol TCP -LocalPort 1514 -Profile Any

# Optional: restrict RDP to the lab network only, never from anywhere
New-NetFirewallRule -DisplayName "RDP from lab net only" `
  -Direction Inbound -Action Allow -Protocol TCP -LocalPort 3389 `
  -RemoteAddress 10.0.0.0/24 -Profile Any

# Confirm both
Get-NetFirewallRule -DisplayName "Wazuh*" | Format-Table DisplayName, Enabled, Direction, Action -AutoSize
Get-NetFirewallProfile  | Format-Table Name, Enabled, DefaultInboundAction -AutoSize
Why only inbound 1514, and nothing else

The agent initiates connections out to the manager on port 1514 and receives replies. Outbound is allowed by default, so that direction needs no rule. The inbound 1514 rule lets the manager accept a push connection and makes troubleshooting from the manager straightforward. Do not expose 55000 or 9200 — those are the manager API and the indexer, and opening them to a lab subnet is a real and extremely common mistake.

P2.5 Verify, properly

# 1. Is it listening?
netstat -ano | Select-String ":1514|:55000"

# 2. Is the service running and set to auto?
Get-Service Wazuh | Format-Table Name, Status, StartType -AutoSize

# 3. Read the agent's own log - this tells you exactly what it is doing
Get-Content "C:\Program Files (x86)\ossec-agent\wazuh-agent.log" -Tail 30

# 4. Can it reach the manager? (this is the real test)
Test-NetConnection -ComputerName 10.0.0.40 -Port 1514

P2.6 Confirm in the dashboard

Refresh Agents. Status should go Pending → Active within about 30 seconds. Then verify real data, not just a heartbeat:

rule.level:>=0 AND agent.name:"winsrv-01"

On a fresh server you should immediately see events from the System channel (service starts, boot), Application, and — once auditing is on in Part P4.4 — Security. If you see only a heartbeat and nothing else, the agent is connected but has nothing interesting to report yet — which is exactly the state you want to be in before hardening.

P2.7 Add labels so filtering stays sane

# In the dashboard: Agents -> winsrv-01 -> Labels

curl -sk -X POST "https://localhost:55000/agents/002/labels" `
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' `
  -d '{"labels":["env.lab","os.windows","os.server2022"]}'

Within a few weeks you will have many agents and no memory of what any of them are. Labels are how you answer “show me every domain controller” without remembering names.

Before you change anything, know what you are dealing with. This whole part is observation only — nothing here modifies the server. It does generate log events, which is useful: you are building the alert baseline from Part P5 as a side effect.

P4  Harden it — the main event

Ordered roughly by impact on your SIEM. Sections P4.1 to P4.3 are good practice on any server; P4.4 is the one your Wazuh lab cannot work without.

Take a snapshot before starting this part

Several of these changes are not easily reversible, particularly Credential Guard and LSA protection. Power off and snapshot as winserver-audited-30sep. Recovering a server you cannot log into is a genuinely bad afternoon, and this makes it impossible.

P4.1 Accounts and passwords

# --- current state ---
net accounts
Get-LocalUser | Format-Table Name, Enabled -AutoSize

# --- password policy: min 14 chars, max age 60 days ---
net accounts /minpwlen:14 /minpwage:1 /maxpwage:60 /lengthenable:yes

# --- account lockout: 5 failures, 15 minutes ---
net accounts /lockoutthreshold:5 /lockoutduration:15 /lockoutobservation:30

# --- disable the Guest account ---
net user guest /active:no

# --- who is actually an admin? ---
Get-LocalGroupMember -Group "Administrators" | Format-Table Name, PrincipalSource -AutoSize
net localgroup Administrators
ControlWhy
Minimum length ≥ 14The single most effective password control. Length beats complexity rules — people reuse complex passwords and guess long ones.
Maximum age 30–60 daysForces rotation. There is real disagreement in the industry about whether this helps; the CIS benchmark requires it, so the benchmark wants it.
Lockout at 5 / 15 minutesTurns online guessing into a non-viable strategy. Know the trade-off: it can also be used to lock out a legitimate user. That is a known denial-of-service consideration you should be able to discuss in an interview.

Use a named admin account, not Administrator

Create labadmin, add it to Administrators, use it for everything, then disable the built-in account. This is a standard CIS recommendation: a guessable, always-enabled, universally-known account name is a gift. Be certain your labadmin credentials work before disabling Administrator.

New-LocalUser -Name "labadmin" -Password (Read-Host -AsSecureString) `
  -Description "Lab admin account"
Add-LocalGroupMember -Group "Administrators" -Member "labadmin"
# test the new login FIRST, in a second session, then:
Disable-LocalUser -Name "Administrator"

Remove stale accounts

Get-LocalUser | Where-Object { $_.LastLogon -lt (Get-Date).AddMonths(-6) }
Get-LocalUser | Where-Object { $_.PasswordLastSet -eq $null }   # never-set password

P4.2 SMB hardening — the highest-value technical change

Check the current configuration

Get-SmbServerConfiguration | Format-List EnableSMB1Protocol, EnableSMB2Protocol, `
  EncryptData, RequireSecuritySignature, EnableSecuritySignature, `
  EnableAuthNullUser, EnableInsecureGuestLogons

Apply

# 1. turn off SMBv1
Get-WindowsOptionalFeature -Online -FeatureName SMB1Protocol
Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol -NoRestart

# 2. require SMB signing on all server-side connections
Set-SmbServerConfiguration -RequireSecuritySignature $true `
                            -EnableSecuritySignature  $true -Force

# 3. require SMB encryption for all shares
Set-SmbServerConfiguration -EncryptData $true -Force

# 4. deny null / anonymous sessions
Set-SmbServerConfiguration -EnableAuthNullUser $false -Force
Set-SmbServerConfiguration -EnableInsecureGuestLogons $false -Force

Verify — the same command you used to read it should now report the new values:

Get-SmbServerConfiguration | Format-List EnableSMB1Protocol, RequireSecuritySignature, EncryptData
Test administration after this, not before

Requiring SMB signing or encryption will break management tools that connect to \\WINSRV-01\C$ from a machine that does not support the new requirement. If you administer from your Windows host, verify a remote administration path works before you apply it. SSH is unaffected, which is another good reason to have installed it in P1.5.

Restrict anonymous access in the registry

$lsa = "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa"
Set-ItemProperty $lsa -Name RestrictAnonymous       -Value 1
Set-ItemProperty $lsa -Name RestrictAnonymousSAM    -Value 1
Set-ItemProperty $lsa -Name restrictnullsessions    -Value 1
Set-ItemProperty $lsa -Name EveryoneIncludesAnonymous -Value 0
Set-ItemProperty "HKLM:\SYSTEM\CurrentControlSet\Services\LanmanServer\Parameters" `
  -Name RestrictNullSessAccess -Value 1

# confirm
Get-ItemProperty $lsa | Select-Object RestrictAnonymous, RestrictAnonymousSAM, restrictnullsessions

P4.3 Protecting credentials on the server itself

LSA protection (RunAsPPL)

Without this, software running on the server can read process memory and extract credentials. With it, the Local Security Authority runs as a protected process and that technique fails.

$lsa = "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa"
Set-ItemProperty $lsa -Name RunAsPPL     -Value 1
Set-ItemProperty $lsa -Name RunAsPPLBoot -Value 1
Restart-Computer

Credential Guard

Runs the LSA in a container isolated from the rest of the OS, using virtualisation-based security. Stronger than LSA protection, and the two work well together.

Enable-WindowsOptionalFeature -Online -FeatureName CredentialGuard -All

Verify with Microsoft's own tool — it prints a table of which protections are active:

C:\Windows\System32\lsaasg.exe /query

Expect Credential Guard: Enabled and LSA protection (RunAsPPL): Enabled. A reboot is generally needed for the full effect.

Why these two matter, in one sentence

Both exist to stop a process that already has administrator from reading plaintext credentials out of memory. That is the most common technique in real Windows intrusions — and it is why “the attacker is already an admin” is not the end of the story.

P4.4 Audit policy — THE most important section for your SIEM

Read this part twice

Without this, Wazuh will show you almost nothing about Windows. With it, you can detect logons, privilege changes, file access, process creation and log tampering — which is the entire difference between a Windows machine in your SIEM and a black box in it.

P5  Validate your detection

You now have a hardened server enrolled in a SIEM. But does the SIEM actually see things? This part proves it, with evidence, by generating controlled activity on your own host.

What makes this legitimate, concretely

Every action below is performed by you, on a machine you own, using your own credentials or a throwaway account you created for this purpose. You are not attacking anything — you are generating log events so your sensor has something to detect. Nothing here tries to gain access to anything, because you already have administrator. That is the whole difference.

P5.1 The method

Choose a technique→ Note the event ID→ Perform it→ Confirm Wazuh alerted→ Record the gap, or fix it

Every test ends with one of two honest outcomes, and both are valuable: “detected, here is the alert” or “not detected, here is the rule I need to write.” A SOC that has only ever seen detections on a dashboard it configured itself does not know its gaps. Finding and closing them is the job.

P5.2 Test 1 — Service and port discovery

Why this matters: service enumeration is the standard first step of reconnaissance. If your SIEM cannot see it, it cannot see the next step either.

# from Kali
sudo nmap -Pn -sV -p- --open 10.0.0.50 --max-rate 500

Where to look in Wazuh:

agent.name:"winsrv-01" AND (rule.groups:portscan OR rule.description:*portscan*)
agent.name:"winsrv-01" AND location:"win_eventchannel"

Write down: did it alert? If not, that is a gap you close in Part P7.

P5.3 Test 2 — SMB share enumeration

# from Kali - read-only enumeration
smbclient -L //10.0.0.50 -N
smbmap -H 10.0.0.50

If your null-session restriction from P4.2 is working, these should now fail:

tree connect failed: NT_STATUS_ACCESS_DENIED

That failure is a good result in itself, and it should still have produced an audit event on the server. Check:

data.win.system.eventID:5140 OR data.win.system.eventID:5145
agent.name:"winsrv-01" AND data.win.system.eventID:5145
If you see nothing at all

That is a real and common finding: the “Other Object Access Events” audit subcategory from P4.4 is what generates 5145. If it is not enabled, Wazuh is blind to file access. Go back and enable it. This is exactly the kind of gap this part exists to find.

P5.4 Test 3 — Failed authentication, and lockout

This is the test most people want to do first, so let us be precise about what it is.

1Create a throwaway test account on the server 
# on WinServer, as labadmin
$pw = ConvertTo-SecureString "A7#kQ2mZ9xR4tB1vC6nH8sD3fG5jL0w" -AsPlainText -Force
New-LocalUser -Name "labtestuser" -Password $pw -PasswordNeverExpires $true `
              -Description "Throwaway account used only for detection testing"
Add-LocalGroupMember -Group "Users" -Member "labtestuser"

You will never need to type that password. You will deliberately send the wrong value, a fixed number of times, to a username you own. That produces log events. It is not an attack, there is no wordlist, and there is no discovery involved.

2Generate the failures from Kali, deliberately 
# ONE known-wrong password, a known number of times, to YOUR OWN account
for i in $(seq 1 8); do
  smbclient //10.0.0.50/IPC$ -U "labtestuser%definitely-not-the-password" -c "quit" >/dev/null 2>&1
  sleep 1
done
Why this is fine, stated plainly

You own both endpoints. The account is one you just created. The password you send is one wrong value you typed on purpose, not a list. The purpose is to make your SIEM emit “failed logon” events so you can confirm it is ingesting and decoding them. Nothing here discovers, targets, or gains access to anything.

3Find the events in Wazuh 
rule.groups:authentication_failed AND agent.name:"winsrv-01"
data.win.system.eventID:4625 AND agent.name:"winsrv-01"

You should see roughly 8 failed logons, then a lockout event once you pass your threshold of 5.

4Find the lockout — event 4740 
data.win.system.eventID:4740

This is the one that matters most. A burst of failed logons is noise; an account actually being locked out is a signal. Check whether your frequency rule from Part P7 fires, and whether Wazuh's stock rules correlate the eight failures into one meaningful alert rather than eight separate ones. That judgement — noise versus signal — is the actual detection skill.

5Clean up 
# on WinServer
Unlock-LocalUser -Name "labtestuser"
Remove-LocalUser -Name "labtestuser"

Leaving a test account with a known password on a server is precisely the thing you would criticise in someone else's configuration. Do not leave it.

P5.9 Test 8 — Log tampering

One of the highest-value detections in all of security: if someone clears the audit log, they know they were noticed and are covering tracks.

Do this test with extreme care, and only once

Clearing the Security log destroys the history you need. Before doing it: (1) take a VM snapshot, (2) export the current log, (3) be certain you have SSH or the console available. Better: verify the rule first, and only run the live test if you really want the proof.

# 1. back it up BEFORE anything else
wevtutil epl Security C:\Windows\Temp\Security-backup.evtx
# 2. confirm you can still get in another way
# 3. only then, if you choose to proceed:
#    Clear-EventLog -LogName Security

When you do run it, the resulting event is 1102 “The audit log was cleared”, and it is generated as part of the clear:

data.win.system.eventID:1102
rule.description:*log*cleared*
rule.groups:log_cleared

This detection works even if the attacker clears everything else, because Wazuh is already streaming the event to the indexer on another machine. That architectural property — centralised, remote, tamper-resistant logging — is the strongest argument for a SIEM, and this test is the most convincing demonstration of it you can run.

P6.3 Sysmon — the single best telemetry upgrade

Sysmon is part of Sysinternals (Microsoft). It writes one consolidated, high-quality log of process creation, network connections, file creation and registry changes — precisely the things that matter for detection. Wazuh decodes Sysmon natively, so no custom decoder is needed.

Install

# download Sysmon from the official Sysinternals site, then:
Expand-Archive -Path .\Sysmon.zip -DestinationPath C:\Sysmon
cd C:\Sysmon
.\Sysmon64.exe -i          # install with default config
.\Sysmon64.exe -c          # check the active config

Configure

The default config is reasonable, but a tuned config is much better. Download the vetted configuration published with Sysinternals and apply it:

.\Sysmon64.exe -c .\SysmonConfig.xml
Restart-Service Wazuh

Sysmon config is XML with two kinds of rule — include (capture these) and exclude (ignore these, to control volume). Anything neither included nor excluded is not captured. A minimal config covering the detection-relevant events:

<Sysmon schemaversion="4.90">
  <EventFiltering>
    <!-- Event ID 1: process creation, with full command line -->
    <ProcessCreate onmatch="include">
      <CommandLine condition="is any"/>
      <OriginalFileName condition="is any"/>
    </ProcessCreate>

    <!-- Event ID 3: outbound network connections -->
    <NetworkConnect onmatch="include">
      <DestinationPort condition="is any"/>
    </NetworkConnect>

    <!-- Event ID 11: file creation -->
    <FileCreate onmatch="include">
      <TargetFilename condition="is any"/>
    </FileCreate>

    <!-- Events 12/13/14: registry create / set / rename -->
    <RegistryEvent onmatch="include">
      <TargetObject condition="contains">CurrentVersion\Run</TargetObject>
      <TargetObject condition="contains">CurrentVersion\RunOnce</TargetObject>
      <TargetObject condition="contains">Services\</TargetObject>
      <TargetObject condition="contains">Windows Defender</TargetObject>
    </RegistryEvent>

    <!-- Event ID 22: DNS queries -->
    <DnsQuery onmatch="exclude">
      <QueryName condition="is any">localhost</QueryName>
    </DnsQuery>
  </EventFiltering>
</Sysmon>
Sysmon is very easy to flood with volume

Event IDs 1 and 11 produce enormous numbers of records on any active machine. Start with narrow include conditions, watch the volume for an hour, and widen only if you need to. Remember Sysmon events arrive in Wazuh as location:win_eventchannel, so if your alert count explodes after enabling it, that is why — and it is a good problem to have, because it means you have process-level visibility.

Verify Sysmon is reporting

  Format-List Id, TimeCreated, Message
# then in Wazuh

data.win.system.eventID:3 AND agent.name:"winsrv-01"

P7.1 Find the field names first

# on SIEM-Ubuntu

    <if_sid>4719</if_sid>
    <description>Audit policy modified on $(SystemName) by $(SubjectUserName)</description>
    <mitre><id>T1562.002</id></mitre>
    <group>windows_defense_evasion,</group>
  </rule>

  <!-- 4740: account lockout. Signal, not noise. -->
  <rule id="100306" level="8">
    <if_sid>4740</if_sid>
    <description>Account $(TargetUserName) locked out on $(SystemName)</description>
    <group>windows_authentication,lockout,</group>
  </rule>

  <!-- Correlation: a lockout followed by SUCCESS from the same source.
       This is the rule that separates a typo from a real intrusion. -->
  <rule id="100307" level="13">
    <if_mit sid="100306">0,6,</if_mit>
    <same_source_ip />
    <description>$(TargetUserName) logged on after a lockout - possible credential compromise</description>
    <mitre><id>T1110</id></mitre>
    <group>windows_correlation,credential_attack,</group>
  </rule>

</group>
Why rule 100307 is the best rule in this document

Every individual event it depends on is low-severity and mostly benign. Someone mistyping a password five times is not an incident. But lockout followed by success from the same source means the guessing eventually worked — and no amount of watching the individual events would have shown you that. This is what correlation means, and it is the difference between a SIEM that shows alerts and one that shows incidents.

P9.1 Turn this lab into a script

The hardening in Part P4 is a perfect candidate for automation. Package it as harden-server.ps1 that runs on any fresh Windows Server VM, and you have demonstrated repeatability — which is what an employer actually means by “automation”.

# harden-server.ps1 - run as Administrator
param([string]$LabIP = "10.0.0.50")

Write-Host "=== Password and account policy ==="
net accounts /minpwlen:14 /minpwage:1 /maxpwage:60 /lengthenable:yes | Out-Null
net accounts /lockoutthreshold:5 /lockoutduration:15 /lockoutobservation:30 | Out-Null
net user guest /active:no | Out-Null

Write-Host "=== SMB hardening ==="
if (Get-WindowsOptionalFeature -Online -FeatureName SMB1Protocol) {
  Disable-WindowsOptionalFeature -Online -FeatureName SMB1Protocol -NoRestart | Out-Null
}
Set-SmbServerConfiguration -RequireSecuritySignature $true -EnableSecuritySignature $true -Force
Set-SmbServerConfiguration -EncryptData $true -Force
Set-SmbServerConfiguration -EnableAuthNullUser $false -Force

Write-Host "=== Null session restriction ==="
$lsa = "HKLM:\SYSTEM\CurrentControlSet\Control\Lsa"
Set-ItemProperty $lsa -Name RestrictAnonymous         -Value 1
Set-ItemProperty $lsa -Name RestrictAnonymousSAM      -Value 1
Set-ItemProperty $lsa -Name restrictnullsessions      -Value 1
Set-ItemProperty $lsa -Name EveryoneIncludesAnonymous -Value 0

Write-Host "=== LSA protection and Credential Guard ==="
Set-ItemProperty $lsa -Name RunAsPPL -Value 1
Enable-WindowsOptionalFeature -Online -FeatureName CredentialGuard -All | Out-Null

Write-Host "=== Audit policy ==="
auditpol /backup /file:"C:\Windows\Temp\audit-backup.csv"
auditpol /set /subcategory:"Logon" /success:enable /failure:enable | Out-Null
auditpol /set /subcategory:"Special Logon" /success:enable | Out-Null
auditpol /set /subcategory:"Logon (Service Package)" /success:enable | Out-Null
auditpol /set /subcategory:"Credential Validation" /success:enable /failure:enable | Out-Null
auditpol /set /subcategory:"Account Lockout" /failure:enable | Out-Null
auditpol /set /subcategory:"Security Group Management" /success:enable | Out-Null
auditpol /set /subcategory:"User Account Management" /success:enable | Out-Null
auditpol /set /subcategory:"Audit Policy Change" /success:enable | Out-Null
auditpol /set /subcategory:"Detailed File Share" /success:enable | Out-Null
Set-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" `
  -Name AuditProcessCreationIncludeCmdLine_Enabled -Value 1

Write-Host "=== PowerShell logging ==="
$ps = "HKLM:\Software\Policies\Microsoft\Windows\PowerShell"
New-Item "$ps\ScriptBlockLogging" -Force | Out-Null
Set-ItemProperty "$ps\ScriptBlockLogging" -Name EnableScriptBlockLogging -Value 1

Write-Host "=== Firewall ==="
Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled True `
  -DefaultInboundAction Block -DefaultOutboundAction Allow
New-NetFirewallRule -DisplayName "Wazuh Agent 1514" -Direction Inbound `
  -Action Allow -Protocol TCP -LocalPort 1514 -Profile Any -ErrorAction SilentlyContinue | Out-Null

Write-Host "=== Networking ==="
Set-NetIPInterface -InterfaceAlias "Ethernet" -Dhcp Disabled -ErrorAction SilentlyContinue
if (-not (Get-NetIPAddress -InterfaceAlias "Ethernet" -AddressFamily IPv4 `
           -ErrorAction SilentlyContinue | Where-Object IPAddress -eq $LabIP)) {
  New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress $LabIP -PrefixLength 24
}

Write-Host ""
Write-Host "=== Verification - compare against your baseline ===" -ForegroundColor Cyan
Get-SmbServerConfiguration | Format-List EnableSMB1Protocol, RequireSecuritySignature, EncryptData
auditpol /get /subcategory:"Logon"
Get-NetFirewallProfile | Format-Table Name, Enabled, DefaultInboundAction -AutoSize
Write-Host "Reboot required for Credential Guard and LSA protection to fully apply."
Run it against a snapshot, not against your working server

This is exactly the kind of thing to test on a throwaway VM. That is what snapshots are for. And notice the script ends by printing its own verification — automation that checks its own work is the difference between a script and a tool.
