Scope — what this reference covers

One page of truth first, then the matrix. Wazuh does not invent Windows telemetry — it ships what the Windows auditing subsystem records. The difference between a quiet lab and a deafening one is almost always audit policy being turned on.

The five Wazuh fields you will actually use
Field
agent.nameWhich machine (use <SERVER> or the agent name you chose).
data.win.system.eventIDThe Windows Event ID (e.g. 4625). Older indexes: win.system.eventID.
data.win.system.severityThe source's own severity hint, if present.
rule.levelWazuh's 0–15 assessment. 8+ = investigate, 12+ = respond.
rule.groupsTags like windows, sysmon, authentication_failures.

To confirm which field names your install uses, click any 4625 alert and inspect its JSON — it takes ten seconds and removes all guesswork.

1  First: make sure Windows will tell you anything

Wazuh's agent forwards events Windows already logged. If audit policy is off, attacks slip past silently no matter how good your SIEM is. Run this on the DC (console or shell) once:

auditpol /get /category:* | findstr /i "Logon Advanced Audit"
Audit category to confirmKey subcategories
Logon/LogoffLogon, Logoff, Account Lockout — feeds 4624/4625/4740
Account LogonKerberos Service Ticket, Kerberos Authentication Service — feeds 4768/4769
Detailed TrackingProcess Creation (with command line) — feeds 4688 and 4104
DS AccessDirectory Service Access — feeds the DCSync 4662
Account ManagementUser/Group Management — feeds 4720/4732
1Turn on process command-line auditing (huge for any red-team lab): 
reg add "HKLM\Software\Microsoft\Windows\CurrentVersion\Policies\System\Audit" ^
  /v ProcessCreationIncludeCmdLine_Enabled /t REG_QWORD /d 1 /f
2Turn on the other categories if they read "No Auditing": 
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Logoff" /success:enable /failure:enable
auditpol /set /subcategory:"Account Lockout" /success:enable /failure:enable
auditpol /set /subcategory:"Kerberos Service Ticket Operations" /success:enable /failure:enable
auditpol /set /subcategory:"Kerberos Authentication Service" /success:enable /failure:enable
auditpol /set /subcategory:"Process Creation" /success:enable /failure:enable
auditpol /set /subcategory:"Directory Service Access" /success:enable /failure:enable
auditpol /set /subcategory:"User Account Management" /success:enable /failure:enable
auditpol /set /subcategory:"Security Group Management" /success:enable /failure:enable
3On the DC, also flag the object that DCSync touches (so 4662 fires): 
Set-ADObject -Identity "CN=Replicator,CN=Users,DC=corp,DC=local" ^
  -Audio:Apply- 2>$null
auditpol /set /subcategory:"Directory Service Access" /success:enable /failure:enable

Full replication-GUID auditing is a small project (Volume 5 does not batch it for you). The reliable lab shortcut: pair Sara's guidance on "Directory Service Access" with the search in Part 2 — seeing some DS-access events is a good start.

The settings that make a lab honest

No audit policy = no events = no fun. Before every campaign, confirm the DC logs 4624/4625/4688. It takes two minutes and saves an hour of "why is Wazuh quiet?".

3  Timeline reads — four searches that tell the whole story

Instead of chasing single events, read the attack as a timeline. These four searches, run in order with a time window, reproduce the intrusion the way a security operations centre would.

3.1 The entrance

agent.name:<SERVER> AND rule.level:>=8 AND !(data.win.system.eventID:(4662))

“Everything notable on the DC that is not routine DS access.” First look of every shift.

3.2 The brute that opened the door

agent.name:<SERVER> AND data.win.system.eventID:4625
# then flip '4625' to '4624' in the same window to find the success that followed

3.3 The hands-on-keyboard part

agent.name:<SERVER> AND data.win.system.eventID:(4688 OR 4104)

3.4 The payoff

agent.name:<SERVER> AND data.win.system.eventID:4662

If you see 4625 → 4624 → 4688/4104 → 4662 in sequence from 10.0.0.30, you are looking at a replay of Volume 4. That ordering is the fingerprint to hunt for.

4  Writing local rules for the gaps

Stock Wazuh is good, but your lab has two classic gaps. Volume 1 showed the local_rules.xml mechanics; here are the two rules worth having.

4.1 The 4662 problem — detect DCSync even without full GUID tuning

If replication-file auditing is too fiddly, catch the shape: a single source object access read storm on the DS from a non-DC host. A frequency rule is the honest fix:

<rule id="100120" level="12" frequency="6" timeframe="120">
  <if_sid>60122</if_sid>
  <same_source_ip />
  <description>Rapid LDAP object access from one source - possible DCSync enumeration</description>
  <mitre><id>T1003.006</id></mitre>
</rule>
  • frequency="6" timeframe="120" — six matching events within two minutes.
  • same_source_ip — the six must come from one host.
  • if_sid 60122 — an existing logon/DS rule to chain onto; adjust to a rule your install actually fires (search data.win.system.eventID:4662 in Dev Tools → Rules).

4.2 Spray / brute-force frequency rule (catch it before lockout)

<rule id="100121" level="10" frequency="8" timeframe="180">
  <if_sid>60122</if_sid>
  <same_source_ip />
  <description>Eight or more Windows logon failures from one source in 3 minutes</description>
  <mitre><id>T1110.003</id></mitre>
</rule>

4.3 Deploy and verify

sudo /var/ossec/bin/wazuh-logtest -t
sudo systemctl restart wazuh-manager
sudo /var/ossec/bin/agent_control -R 002      # agent 002 = WinServer; refresh its config

Then re-run the spray from Volume 4 and watch 100121 fire around guess eight. A rule that never fires in Wazuh is a rule you never tested.

5  Tuning: from "everything" to "everything interesting"

  • Start at level 8. Low-severity noise (cron, sudo, routine logins) will drown you. Triage at rule.level:>=8, drill down only when investigating.
  • Filter to the agent that matters. A lab with Kali + DC + client is three very different noise profiles. Separate them with agent.name:<HOST>.
  • Baseline before you attack. Spend one hour just watching; what fires normally becomes boring, and only the deltas deserve your attention.
  • Suppress, don't disable. When a rule is useless, lower it in local_rules.xml rather than deleting the group, so you can raise it later.
  • Alert fatigue is the enemy. If everything is critical, nothing is. Ten tuned medium rules beat 200 shrieking ones.

6  Keeping the pipeline alive

A SIEM you do not maintain is a screenshot, not a security tool. Two things keep this lab honest: know the arrow, and know the failure that broke it once before.

6.1 The arrow

Agent→ manager→ alerts.json→ filebeat→ indexer→ dashboard

When something does not appear in the UI, debug along this arrow in this order.

6.2 The one that bit you (and now lives in your playbook)

filebeat crashed at boot with a seccomp error — fixed 10 Oct 2026

Symptom: wazuh-manager/indexer/dashboard all active, filebeat failed, dashboard showing no new alerts. Logs screamed runtime/cgo: pthread_create failed: Operation not permitted — filebeat's built-in seccomp filter does not allow the clone3 syscall that glibc uses on a new kernel (Ubuntu 26.04 / kernel 7.0), so the very first extra thread kills the process.

Fix applied: appended to /etc/filebeat/filebeat.yml:

seccomp:
  enabled: false

Then sudo systemctl reset-failed filebeat and sudo systemctl start filebeat. Credentials resolve from the filebeat keystore (/var/lib/filebeat/filebeat.keystore), not the config.

6.3 Routine health check (one line)

systemctl is-active wazuh-manager wazuh-indexer wazuh-dashboard filebeat
sudo curl -sk -u 'admin:<your-admin-pass>' 'https://127.0.0.1:9200/_cluster/health?pretty'

Four active + cluster green = the pipeline is fine and any quietness is a detection problem, not an infrastructure problem.
